# Landing and finite delivery — next connected mechanisms

Research notes, 2026-10-10. This is not implemented landing or delivery, and does not change the current flight/propulsion models.

The current spacecraft retains first spherical contact with its incoming velocity and finite cargo. A terminal impact record is insufficient evidence for unloading into a geographic habitat. Next builds need actual surface-relative position/velocity, supported terrain/source registration, a defined contact response and retained inventory exchanges. Preserve the verified design bench and versioned flight recordings when adding those mechanisms.

[NASA's Apollo landing-gear experience report, NASA TN D-6850 (1972)](https://ntrs.nasa.gov/api/citations/19720018253/downloads/19720018253.pdf), introductory discussion and landing-performance appendix, treats touchdown as a stability, energy absorption, structural loading and surface-condition problem. This supports implementing contact response and geometry instead of declaring a landing from a low centre-of-mass speed alone. Its hardware-specific envelopes are not universal safe limits for arbitrary authored vehicles.

[NASA SPLICE](https://www.nasa.gov/safe-and-precise-landing-integrated-capabilities-evolution-splice/) describes integrated surface navigation, terrain/hazard assessment and descent guidance. That motivates exposing target-frame observations and measured-versus-modeled support before an automatic descent controller. It does not supply calibration or accuracy guarantees for this application's terrain or vehicle model.

The next mechanism should establish local rotating surface-relative observations, approach geometry, explicit finite touchdown energy/force assumptions and an honest supported contact/attachment regime. Airless descent is a useful connected starting point while atmosphere/entry remains incomplete, but must still include actual gravity, finite burns and surface motion. Do not reinterpret a retained spherical impact as a safe landing, teleport a craft to a site, or replace descent with a timer.

Physical transfer must require supported co-location with the exact habitat body/site and bounded relative motion, withdraw from the same retained craft inventory, respect habitat capacities, retain rejected/excess stock, and apply atomic ordinary edits with exact undo/save/replay. Inspect the actual habitat inventory semantics before mapping all four cargo materials; equal display names are insufficient. Initial authored cargo remains distinct from later stock loading. No implicit settlement grant, waste sink, doubled stock or food/chemical-energy credit.

Keep the graphics supplement queued. These mechanisms need scientific state, controls and numerical evidence first; detailed vessel/planet assets are a separate rendering build. Landing hardware certification, crew safety, atmospheric entry, uncertainty and complete supply-chain acceptance remain unproven.

## Rotating arrival mechanism (implementation in progress)

[JPL NAIF rotation required reading, state transformations](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/req/rotation.html#State%20transformations) establishes that transforming velocity needs the time derivative of the frame rotation as well as the rotated velocity. Engineering requirement: subtract body translation and `omega × relative_position`, then apply the same inverse tilt/spin used by existing terrain coordinates. Implement the inverse too, so geographic starts specify actual east/north/up velocity without hand-built system-axis vectors. Fixed-spin rates use the stored period; tidally locked rates differentiate the existing parent-facing azimuth, including its projected orbital motion. This is the application's modeled frame, not an imported IAU/SPICE orientation solution.

Existing on-rails dynamics may expose a physical velocity initialized with a two-body mass parameter while positions advance with the rail's anomaly parameter. Frame translation must differentiate the actual modeled position rather than treating that initialization velocity as its exact derivative. Geographic flight definitions convert the resulting absolute initial velocity back through the existing ordinary create convention; do not change existing dynamics or versioned flight records to conceal the distinction.

Approach observations should retain radius/clock/frame/terrain support, signed radial speed, horizontal speed and kinetic energy. Overview terrain clearance is separate from the existing spherical collision boundary; source-interpolated relief is not a validated landing site. Pole east/north/longitude are unavailable when the tangent basis is undefined. Unsupported/historical live terminal states must not borrow current planet orientation and call it original touchdown evidence. A separately replayed approach report can retain the first resolved terminal observation without moving the craft or crediting settlement resources.

## Next physical contact build

Implement contact evolution as a new explicitly versioned flight capability, preserving the current model/recordings. The landing mechanism must use the same modeled rotating terrain geometry as site observations, not attach every old spherical impact to a site. Retain finite gear/contact assumptions (stroke, restoring/damping forces, friction and supported structural limits), integrate contact motion/energy, and expose failed/unsupported response. A low centre-of-mass speed or a completed descent timer cannot establish attachment. Resolved rotation, attitude/slope/footprint support and atmospheric limitations must remain explicit. A spherical reference fixture alone does not complete terrain landing in the directive.

Only after supported contact can a stock-transfer edit check the actual craft/site geometry and bounded relative motion, then debit/credit conservative material inventories with remaining cargo and rejection reasons. Launch, staging, orbital transfers, entry/heating, power/thermal/communications/shielding, free-follow cameras and state-driven vehicle effects remain separate required phase-10 work. This arrival build is a necessary shared mechanism; it does not reduce that scope.
